# Architecture

Forever Sandbox is four programs and an addon. The player only ever starts `ForeverSandbox.exe`; it runs everything else.

| Component | Source | Output in the product folder |
| --- | --- | --- |
| Launcher | `src/ForeverSandbox` | `ForeverSandbox.exe` |
| Server | `src/ForeverSandbox.Server`, `src/ForeverSandbox.Framework` | `server\ForeverSandbox.Server.exe` |
| Snapshot tool | `src/ForeverSnapshot` | `tools\ForeverSnapshot.exe` |
| Certificate tool | `src/ForeverCertificates` | `tools\ForeverCertificates.exe` |
| SandboxTools addon | `addons/SandboxTools` | `client\_classic_beta_\Interface\AddOns\SandboxTools` |

## Product folder

```text
ForeverSandbox.exe     launcher
sandbox.json           settings: clientRoot, realmKeyWrite, fullFogOff
server\                the sandbox server (self-contained .NET 8)
tools\                 ForeverSnapshot.exe, ForeverCertificates.exe
sandbox-data\          characters.json, account-data.json, locations.json (the player's) and hotfixes.json (shipped)
certificates\          the local login certificates and what the launcher trusted
state\run-<UTC>\       one folder per run: server logs, ready.json, diagnostics
client\                the frozen 1.60.1.70338 client snapshot (made locally, never shared)
```

## What happens on `ForeverSandbox.exe`

1. **Snapshot check.** `client\snapshot.json` must exist and `WowB.exe` / `WowB_loader.dll` must match the 1.60.1.70338 hashes.
   The server only speaks this build's protocol.
2. **Certificates.** The client logs in over TLS, so the launcher keeps a local chain valid: a name-constrained root that can
   only sign `localhost` / `127.0.0.1`, and a leaf for both. `ForeverCertificates` creates them (the root's private key is
   destroyed right after signing). The root goes into the CurrentUser root store (Windows asks once) and is renewed 14 days
   before it expires. Only entries the launcher added are ever removed.
3. **Server.** `server\ForeverSandbox.Server.exe` starts hidden with a fresh state folder and listens on loopback:
   8000 (Battle.net RPC over TLS), 8001 (REST login), 8085 (realm) and 3724 (instance). The launcher waits for its
   `ready.json` and checks that the login port presents the expected certificate.
4. **Client.** `WowB.exe -config ForeverSandbox.wtf`: the config points the portal at `127.0.0.1:8000`. Every other setting
   the game saves in that file is kept between runs.
5. **Realm key (opt-in).** The client authenticates the world server's `EnterEncryptedMode` with Ed25519 public keys from a
   table in its own memory. With the player's permission (asked once, stored as `realmKeyWrite`), the launcher validates that
   table and replaces one 32-byte public key with the sandbox's. Without it, login and characters work but entering the world
   does not. Nothing on disk changes.
6. **While the game runs.** The launcher keeps the fog monitor ([fog.md](fog.md)) and the wall overlay ([walls.md](walls.md))
   running. Closing the game stops the server.

## Server

The server is a .NET 8 console program. `LocalServerHost.cs` is its entry point.

- `AuthServer/Network/Bgs*.cs`, `LocalLoginRest.cs`, `DemoSrpSession.cs`: the Battle.net login. The REST login runs SRP
  (account `admin`, password `admin`). The RPC services cover authentication, account, game utilities and the realm list,
  which holds one realm, "Forever Sandbox".
- `WorldServer/Network/Forever*.cs`: the 1.60.1.70338 world protocol.
  - Handshake and AES-GCM session encryption (`ForeverWorldHandshake`, `ForeverWorldCrypto`, `Ed25519Ctx`).
  - Characters (`ForeverCharacters`) and world entry (`ForeverWorldEntry`).
  - Update fields (`ForeverUpdateFields.g.cs`, generated by `tools/gen_update_fields.py`).
  - Hotfixes (`ForeverHotfixes`) and movement and chat commands (`ForeverFlight`, `ForeverTeleport`).
  - Terrain from the client's own files (`ForeverCasc`, `ForeverTerrain`) and the impassable walls (`ForeverImpass`,
    `ForeverGameObjects`, `ForeverWallModels`).
- `WorldServer/Managers`, `WorldServer/Game`, `Resources/`: older shared game logic and data tables, still loaded at start.

The client waits for its TACT decryption keys before it shows the character screen. They come from
`sandbox-data\hotfixes.json` as hotfix pushes. That file is built by `tools/extract_reference_hotfixes.py`.

## Snapshot

`ForeverSnapshot create --from "C:\Blizzard Games\World of Warcraft" --to <product>\client` copies exactly one build out of the
shared Battle.net storage: its program folder, build and CDN configs, and the storage content its manifests reference. It
produces a standalone install with a one-row `.build.info`, so Battle.net never updates it. The copy only reads the source and
can be resumed. `verify` re-hashes the copy.

`ForeverSnapshot walls install|remove|status` adds or removes the sandbox's own client files, which are the wall models
([walls.md](walls.md)).

## Tests

`tests/ForeverSandbox.Tests` is a console program run by `scripts/Test.ps1`. It covers:

- login framing, SRP vectors and the realm list;
- world handshake keys against an independent Python derivation (`world_keys_reference.py`);
- packet layouts from captured client bytes;
- character storage, hotfix rows and game objects.

With a client present (`-Client <snapshot>` or the Battle.net install), it also reads real terrain, client tables and
impassable walls.
